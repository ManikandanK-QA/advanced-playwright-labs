Four Playwright disciplines that most portfolios mention and few demonstrate
properly: **visual regression**, **network simulation**, **performance budgets**
and **browser security** — each with a deterministic target, a real failure path,
and a negative control that proves the measurement actually works.

The target application lives in this repository (`apps/lab-site`) and is served by
a zero-dependency Node server. That is deliberate: a third-party demo cannot hand
the suite a CSP it can assert, an HttpOnly cookie it can probe, or a page with a
known performance regression baked in.

## What each lab proves

| Lab             | Evidence                                                                                                                                                                                           | Tests |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----- |
| **Visual**      | Pixel comparison against baselines built inside the pinned Playwright Linux image, with an absolute diff allowance                                                                                 | 5     |
| **Network**     | Mocked 200/503/abort responses, a held request that proves the loading state, exact POST body capture, and a ledger that fails any unmocked API call                                               | 8     |
| **Performance** | LCP, CLS, TTFB, DOMContentLoaded and long tasks collected with `PerformanceObserver` and gated by budgets in one config file                                                                       | 3     |
| **Security**    | CSP enforced (inline script blocked, injected handler never runs), cookie flags verified through `document.cookie` **and** context cookies, hardening headers asserted on documents, JSON and 404s | 11    |

27 test definitions; 49 executions in CI because the security suite runs on
Chromium, Firefox and WebKit.

## Quick start

```bash
git clone https://github.com/ManikandanK-QA/advanced-playwright-labs.git
cd advanced-playwright-labs

npm ci
npx playwright install chromium

npm test          # every project; visual is skipped off Linux
npm run report    # open the last HTML report
```

The lab server starts automatically through Playwright's `webServer`. To browse
the target yourself:

```bash
npm run site      # http://127.0.0.1:4173
```

## The target site

```
apps/lab-site/
  server.mjs                  headers, cookies, JSON endpoints, delay/failure injection
  public/
    index.html                lab index
    visual/                   dashboard + pricing, fully static
    network/                  feed + checkout with real async states
    performance/              stable baseline + deliberately regressed page
    security/                 CSP lab, cookie lab, storage lab
    assets/                   CSS, classic scripts, inline SVG hero
```

Everything renders from hardcoded data. No web fonts, no CDN, no dates, no random
identifiers — so a screenshot taken today matches one taken next month inside the
same browser image.

## Hermetic network tests

Every test receives a `ledger` fixture automatically. At teardown it fails the test
if a request left the lab origin, and — when `requireApiMocks` is enabled — if any
`/api/` call was not answered by a registered mock.

```ts
test.use({ requireApiMocks: true });

test('keeps the loading state visible while the request is in flight', async ({ page, ledger }) => {
  let release = (): void => {};
  const gate = new Promise<void>((resolve) => {
    release = resolve;
  });

  await ledger.route('**/api/feed', async (route) => {
    await gate; // hold the response open
    await jsonHandler(200, feedBody())(route);
  });

  const feed = new FeedPage(page);
  await feed.open();

  await expect(feed.loading).toBeVisible(); // no sleep, no race
  release();
  await feed.waitForArticles(2);
});
```

The test is deterministic on a fast laptop and on a loaded CI runner, because the
response is released by the test, not by a timer.

## Performance budgets

| Metric                | Budget   | Rationale                                                  |
| --------------------- | -------- | ---------------------------------------------------------- |
| LCP                   | 2 500 ms | Core Web Vitals "good" threshold                           |
| CLS                   | 0.10     | Core Web Vitals "good" threshold                           |
| TTFB                  | 800 ms   | local server: slower means the page or harness is at fault |
| DOMContentLoaded      | 2 000 ms | one stylesheet and one image                               |
| Long tasks (baseline) | 0        | any 50 ms+ block on a static page is a defect              |

`/performance/heavy.html` injects a 120 px layout shift and an 80 ms long task
after load. A test asserts those are **detected** — if the observer pipeline
breaks, that test fails before the passing budgets can mislead anyone.

## Visual baselines

Baselines are generated in `mcr.microsoft.com/playwright:v1.65.1-noble` by a
manual CI run, then committed. The suite compares with an absolute allowance of
100 pixels, not a percentage.

That detail came out of verification: the first version used a 1 % ratio, and a
chart stroke colour change passed. A ratio gives large pages a larger free
allowance, which is exactly backwards. See
[docs/visual-baselines.md](docs/visual-baselines.md).

## CI/CD

```
quality ── typecheck · lint · format
   │
labs (matrix, all inside the pinned Playwright image)
   ├─ visual      ├─ performance       └─ security-webkit
   ├─ network     ├─ security          └─ security-firefox
   │
report ── merge shard blobs → HTML report → artifact (+ gh-pages on main)
```

- Each lab runs in its own job, so one failure cannot mask another.
- A version guard fails the build if `@playwright/test` and the container tag
  disagree, because that silently changes screenshot rendering.
- `workflow_dispatch` with `update_visual_baselines` regenerates baselines in the
  same image that compares them.

Details: [docs/ci.md](docs/ci.md).

## Design decisions

**A server instead of a mock.** Asserting `Content-Security-Policy` against a
static host's responses would test nothing. The lab server owns the header
contract, the cookie attributes and the endpoints the UI calls.

**An HttpOnly cookie plus a readable one.** Proving `session` is invisible to
`document.cookie` means nothing if cookies are broken. The `theme` cookie is the
positive control: it is visible, so the absence of `session` is meaningful.

**Content assertions before screenshot assertions.** A blank page compared against
a blank baseline is a green test. Every visual test asserts a heading, a count or
a value before it compares pixels.

**Absolute diff allowance.** See above — a ratio hid a real colour regression
during verification.

**Negative controls.** The heavy performance page must fail its budgets, and the
visual pipeline must react to a changed colour. A suite that has never failed is
not evidence.

**No retries.** A visual or performance test that only passes on the second
attempt is a finding, not a pass.

## Limitations

- The visual suite is Linux-only by design; developers on other platforms see it
  skipped.
- The security lab is served over HTTP, so `Secure` cookies and HSTS are out of
  scope here (asserting them would test a header string while the browser drops
  the cookie). That belongs in a TLS-terminated environment.
- Performance numbers are for a localhost target; they gate regressions in the
  page, not real-user network conditions.
- Visual baselines must be regenerated whenever Playwright is upgraded, because
  the renderer changed.
